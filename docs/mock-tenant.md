# Mock tenant

`cpictl mock-tenant` serves an in-memory mock of the SAP CPI APIs that cpictl uses. It is for
local development, demos, end-to-end tests of tools built on cpictl (such as a UI or an agent)
and CI. It never talks to a real tenant. By default any credentials are accepted;
`--credentials strict` checks them like a tenant (see [Credentials](#credentials)).

```bash
cpictl mock-tenant --tier dev --addr 127.0.0.1:8081
```

It prints the settings to connect:

```
CPICTL_TMN_HOST=http://127.0.0.1:8081
CPICTL_TMN_USERID=mock
CPICTL_TMN_PASSWORD=mock
# or OAuth: CPICTL_OAUTH_HOST=127.0.0.1:8081 CPICTL_OAUTH_CLIENTID=mock CPICTL_OAUTH_CLIENTSECRET=mock
CPICTL_RUNTIME_OAUTH_HOST=127.0.0.1:8081
CPICTL_RUNTIME_OAUTH_CLIENTID=mock-rt
CPICTL_RUNTIME_OAUTH_CLIENTSECRET=mock-rt
# credentials any: every credential is accepted (--credentials strict checks them like a tenant)
CPICTL_MOCK_ADMIN_TOKEN=<random token for the /_mock admin API; printed unless you pass --admin-token>
```

State is in memory: a restart resets it. Stop it with Ctrl+C.

## Credentials

A Cloud Foundry tenant has two service keys: the **API key** (plan `api`) manages content through
`/api/v1` but cannot call a flow, the **runtime key** (plan `integration-flow`, role
`ESBMessaging.send`) calls the flows' endpoints (`/http/...`, `/cxf/...`, `/gw/odata/...`) but cannot manage
content. `--credentials` chooses how the mock treats credentials:

| `--credentials` | `/api/v1` | `/http/...`, `/cxf/...`, `/gw/odata/...` | `/oauth/token` |
|---|---|---|---|
| `any` (default) | any credentials | any credentials | a token for any client |
| `strict` | the API user (`--api-user`/`--api-password`, Basic Auth) or API client (`--api-client-id`/`--api-client-secret`, OAuth or Basic Auth); the runtime client gets **403**, anything else **401** | the runtime client (`--runtime-client-id`/`--runtime-client-secret`, OAuth or Basic Auth); the API user or client gets **403**, anything else **401** | a token per client, for the configured clients only (else 401 `Bad credentials`) |

Defaults: API user `mock`/`mock`, API client `mock`/`mock`, runtime client `mock-rt`/`mock-rt`;
all are printed at start. `cpictl send` and the MCP tool `send_test_message` use the runtime
client from `CPICTL_RUNTIME_OAUTH_*` (without it the API credentials, which a strict mock refuses
on the endpoint like a tenant). Use `strict` in tests that must not pass on the mock and fail on a
tenant because the runtime key was forgotten:

```bash
cpictl mock-tenant --tier dev --credentials strict --runtime-client-id rt-client --runtime-client-secret rt-secret
```

In Go tests: `Tenant.Auth` (`mocktenant.Auth`; nil accepts any credentials).

## Demo landscape

`--seed demo` (default) loads one tier of a demo landscape; `--seed empty` starts without content.

| Flow | Package | Started by | Sends to |
|------|---------|------------|----------|
| `Orders_In` | Orders | HTTPS `/orders/in` | ProcessDirect `/orders/route` |
| `Orders_Route` | Orders | ProcessDirect `/orders/route` | HTTP ERP (`ERP_User`), JMS queue `Orders_Billing` |
| `Billing_In` | Billing | JMS queue `Orders_Billing` | ProcessDirect `/billing/post` |
| `Billing_Post` | Billing | ProcessDirect `/billing/post` | HTTP finance (`Finance_OAuth`, key `finance_client`) |
| `Partner_Notify` | Partners | timer | SFTP (`Partner_SFTP`) |
| `Returns_In` (dev only) | Orders | HTTPS `/returns/in` | HTTP returns API (`Returns_API`) |
| `Orders_IDoc_In` | Orders | IDoc `/orders/idoc` (ORDERS05 from ERP) | XML to JSON, HTTP order API (`ORDER_API_URL`) |
| `Orders_OData_Service` | Orders | OData V2 `/gw/odata/Demo/Orders;v=1` (entity set `SalesOrders`, EDMX `edmx/Orders.edmx`) | IDoc receiver to ERP (`ERP_IDOC_URL`, `ERP_User`) |

The Billing package also has a value mapping, `Billing_CountryCodes` (`ERP:Country ->
Finance:CountryCode`, DE/AT/CH), for `cpictl valmap`.

The flows have real `.iflw` models with diagrams (laid out by `iflow layout`), scripts that write
the `OrderNo` custom header property, externalized parameters, and a day of message processing
logs generated by running the flows (see [Execution](#execution)): orders run
`Orders_In → Orders_Route → Billing_In → Billing_Post` with the same correlation ID; about one
posting in twenty fails (the finance system's error, `Billing_In` goes to `RETRY` with it); on test
and prod the ERP call times out now and then; `Partner_Notify` fails now and then; on dev some
orders come back through `Returns_In` with a new correlation ID and the same `OrderNo` (see
[following a message without a tracer](monitoring.md#following-a-message-without-a-tracer));
about two ORDERS IDocs an hour reach `Orders_IDoc_In` (ApplicationMessageId: the IDoc number),
and the order API rejects a few of them. The
demo is itself a landscape (`internal/cpitest/landscapes/demo`).

The tiers differ the way real ones do:

| | dev | test | prod |
|--|-----|------|------|
| `Orders_Route` | 1.0.4 | 1.0.3 | 1.0.2 |
| `Returns_In` | 0.1.0 | – | – |
| `Billing_Post` | draft, locked by `dev.user@customer.example` (open in the Web UI) | 1.3.1 | 1.3.1, `Timeout` changed on the tenant |
| `Returns_API` credential | yes | yes | missing |
| `finance_client` certificate | expires in 300 days | 200 days | **20 days** |
| parameter hosts | `*-dev.example.com` | `*-qa.example.com` | `*-www.example.com` |

So `matrix`, `compare`, `transport check` and `logs summary` all have something to show:

```bash
# one mock per tier, and a profile per tier (~/.cpictl/<tier>.yaml with tmn-host, tmn-userid, tmn-password)
cpictl mock-tenant --tier dev  --addr 127.0.0.1:8081 &
cpictl mock-tenant --tier test --addr 127.0.0.1:8082 &
cpictl mock-tenant --tier prod --addr 127.0.0.1:8083 &

cpictl matrix tenant:dev tenant:test tenant:prod
cpictl compare tenant:test tenant:prod
cpictl --profile dev snapshot --dir-git-repo . --dir-artifacts packages --draft-handling ADD
cpictl transport check Returns_In Orders_Route --dir packages --source tenant:dev --target tenant:prod
cpictl --profile dev logs summary --since 24h
```

## Landscapes (`--seed-dir`)

`--seed-dir <dir>` loads your own landscape instead of the demo, one tier per mock:

```bash
cpictl mock-tenant --seed-dir ./landscapes/retail-b --tier prod-eu --addr 127.0.0.1:8084
```

A landscape directory holds the content in the layout `cpictl snapshot` writes, plus
`landscape.yaml` with everything that differs per tier and what the content does not contain:

```
retail-b/
  landscape.yaml
  packages/<Package>/<Package>.json          # optional: {"d": {"Id", "Name", "Version"}}
  packages/<Package>/<Artifact>/META-INF/MANIFEST.MF
  packages/<Package>/<Artifact>/src/main/resources/...
```

So a snapshot of a real tenant (or `cpictl iflow copy` / templates) is a valid starting point.
The artifact ID comes from `Bundle-SymbolicName`, the name from `Bundle-Name`, the version from
`Bundle-Version`, the type from `SAP-BundleType`.

```yaml
name: retail-b                      # required
description: S/4 orders to Salesforce, invoices to SFTP
keyHeaders: [SalesOrder]            # custom header properties written by the flows' scripts
history: 24h                        # message history generated at start (default 24h)
seed: 7                             # optional: change the generated traffic and failures

tiers:                              # required, in pipeline order; --tier picks one
  - name: dev
    drafts: [SF_Order_Upsert]       # being edited in the Web UI: designtime "Active"
    locks: { SF_Order_Upsert: dev.user@customer.example }   # edit lock (cpictl locks list)
  - name: prod-eu
    versions: { S4_Orders_Out: 1.0.2 }                 # designtime and running version
    parameters: { S4_Orders_Out: { Host: s4-prd.example.com } }   # configured on this tenant
    modifiedBy: { Order_Route: m.okafor@customer.example }       # changed on the tenant (drift)
    exclude: [Returns_In]           # does not exist on this tier
    notDeployed: [SF_Account_Sync]  # exists, not running
    missingCredentials: [SF_OAuth]
    keystore: [{ alias: sf_client, expiresInDays: 12 }]
    partnerDirectory: { Shop_DE/endpoint: "https://shop-de.example.com" }
    systems: { s4: { failRate: 0.1 } }                  # overrides per tier
    trafficScale: 2                 # more messages on this tier (0 or unset: 1; not negative)

systems:                            # receivers the flows call, matched by host
  s4: { match: "s4-*.example.com", latencyMs: 180, failRate: 0.02, status: 500,
        error: "SO {key}: plant 1010 locked ({host})" }

credentials:                        # names only; secrets are never real
  - { name: S4_User, kind: basic, user: RFC_SO }       # kind: basic | oauth2 | secure
  - { name: SF_OAuth, kind: oauth2, tokenUrl: "https://login.salesforce.com/oauth2/token" }
keystore: [{ alias: sf_client, expiresInDays: 300 }]
partnerDirectory: { Shop_DE/format: JSON }

traffic:                            # messages that start at a flow
  - start: S4_Orders_Out            # HTTPS sender or timer flow
    perHour: 40
    key: "SO{n}"                    # business key; {n} counts up from keyStart
    keyStart: 1000
    followUps:                      # the transaction comes back later with a new correlation ID
      - { start: Returns_In, every: 4, after: 20m, tiers: [dev] }
```

Unknown fields, unknown artifacts, credentials, systems or tiers are refused at start (exit 2).
The built-in demo is a landscape of this format (`internal/cpitest/landscapes/demo`).

## Live behaviour

- A deploy starts the designtime version (a draft deploys as the version running before); the
  build task reports `SUCCESS`; an undeploy removes the runtime artifact.
- Uploads (create, update, value mapping changes) set `ModifiedAt` and `ModifiedBy` of the
  designtime artifact like every save on a tenant: `ModifiedBy` is the API user (Basic Auth) or
  the OAuth client of the request (`mock-user` without credentials). The package's artifact list
  and the artifact itself report both. The tenant derives
  what a real one does from the archive: the resources (scripts, mappings, schemas, the model)
  and the externalised parameters from `parameters.prop`. A new upload keeps the configured value
  of a parameter that still exists. Like a real tenant, the upload does not take the version from
  `MANIFEST.MF` (a new artifact gets 1.0.0); with `--versioning manifest` cpictl sets
  `Bundle-Version` after the upload ([versioning.md](versioning.md)).
- A deploy registers the flow's HTTPS (`/http/<urlPath>`), SOAP and IDoc (`/cxf/<address>`) and
  OData V2 (`/gw/odata/<namespace>/<service>;v=<version>`) senders as runtime endpoints, listed
  in `ServiceEndpoints` (`Protocol` `REST`, `SOAP` for `/cxf/`, `ODATA`); an undeploy removes them.
  See [IDoc and OData senders](#idoc-and-odata-senders). So flows uploaded
  into `--seed empty` can receive messages.
  Like on a real tenant, a flow whose address is already used by another deployed flow does not
  start: its deployment ends in `ERROR` with the runtime error information `the address /orders/in
  is already used by Orders_In` (the usual mistake after copying a flow). Undeploying the first
  flow frees the address.
- A message sent to a flow's endpoint (`cpictl send --artifact-id Orders_In`) runs the flow (see
  [Execution](#execution)) and is answered with the payload (or the seed's fixed answer), or with
  HTTP 500 and the error when the run failed.
- Message log queries honour the status, time and equality filters, newest first.
- Message logs added while the mock runs (messages, `--live-traffic`, `/_mock/run`, `/_mock/messagelogs`) are
  kept newest first and bounded: logs older than `--log-retention` (default `168h`; `0` = no age
  limit) **behind the newest log** and everything beyond the newest 100 000 are dropped, so a mock
  left running does not grow without limit. The age is measured from the newest log, not the
  clock: logs added for an earlier period, and a mock seeded in the past, keep their history until
  newer logs push it out. In Go tests: `Tenant.LogRetention` and `Tenant.MaxLogs`.
- Value mappings are read from the artifact's `value_mapping.xml` (groups of a source and a target
  entry); `UpsertValMaps` writes the change back into the archive, so a download shows it. A
  source value that exists twice in a schema, or an unknown agency/identifier pair, is refused.
  Default values are always empty.
- Deleting a designtime artifact keeps a deployed one running; deleting a package deletes its
  designtime artifacts. Deploying with a type the artifact does not have answers 404.
- Security material: key pairs and SSH keys can be generated (the mock creates a real key, so
  `keystore csr` returns a valid PKCS#10 and `upload-chain` accepts the signed chain), entries
  deleted (SAP-owned ones refuse), and the keystore history, PGP keyrings and keys, OAuth2
  authorization code credentials, access policies with artifact references and the audit log are
  served (empty unless set in Go tests: `Tenant.SecurityMaterial`). `Partners`, alternative
  partners and authorized users of the Partner Directory work the same way; parameter listings
  honour `$select` (no values without `Value`).
- Data stores and log files answer with empty lists (also with `--seed empty`); APIs the mock does
  not know answer 404.

## IDoc and OData senders

SAP landscapes start many flows with IDocs and OData requests. The mock serves both sender
adapters; the adapter variants and versions are the editor's (`sap:IDOC` sender 1.4.5, receiver
1.8.3; `sap:ODataSender` 1.3.1), the channel is recognised by its `cmdVariantUri`. What SAP
documents but was **not verified on a tenant** is marked *assumption*; it may differ on yours.

**IDoc sender** (`POST /cxf/<address>`, the channel's `address`; *assumption*: the key and the path
follow the SOAP sender):

- Takes IDoc XML (`application/x-sap.idoc`, `text/xml`, ...) with or without a SOAP envelope; the
  envelope is removed and the flow gets the IDoc XML (the first element of the SOAP Body).
- XML without an `EDI_DC40` control record is refused with **400** and the reason (*assumption*:
  the tenant's answer to a bad IDoc is not known).
- From the first IDoc's control record the flow gets the headers `SapIDocType` (IDOCTYP, or
  CIMTYP for an extension), `SapIDocDbId` and `SapIDocTransferId` (both DOCNUM) — *assumption*:
  the header names are SAP's documentation, their values the mock's choice. In Go tests
  `Tenant.Received` holds them with the control records (`IDocs`: DOCNUM, IDOCTYP, MESTYP, SNDPRN,
  RCVPRN, ...).
- The message log's ApplicationMessageId is the DOCNUM unless the flow sets one (or the request
  has `SAP_ApplicationID`); traffic rules into an IDoc flow use the key padded to 16 digits.
- Answer: **HTTP 200 with an empty body** and the `SAP_MessageProcessingLogID` header, HTTP 500
  with the error text when the run failed (*assumption*: the real adapter may answer with a SOAP
  acknowledgement).

**OData V2 sender** (`/gw/odata/<namespace>/<service>;v=<version>/...`, *assumption*: SAP's
documented path). The sender's property keys for namespace, service and version are not known
from real content, so the mock derives the service root: from the channel's address (`urlPath`,
`address`, ... as for other senders, e.g. `Sales/Orders;v=2`; `;v=1` is added when missing), else
from the flow's EDMX resource (`Schema Namespace` / `EntityContainer Name`, version 1), else
`SAP/<artifact ID>;v=1`.

- `GET .../$metadata` answers the EDMX resource, `GET .../` the service document (entity sets of
  the EDMX); an entity set the EDMX does not have answers 404.
- GET, POST, PUT, PATCH, MERGE and DELETE on an entity set run the flow with the request body.
  The mock executes no mapping, so the answer is the endpoint's `Response` when one is configured
  (`Tenant.Inbound[path]`, `/_mock/state`), else: GET an empty result (`{"d":{"results":[]}}`, or
  `{"d":{}}` with a key), POST **201** with the body passed through, the others **204**; a failed
  run answers 500 with an OData error.

**IDoc receiver**: a receiver like HTTP: the system its `address` host belongs to
(`http://<host>:<port>/sap/bc/srt/idoc?sap-client=<client>`) answers with latency and failures,
in sent messages, traffic and `/_mock/run`; its `credentialName` must exist. A failure ends the
run at the step `Send to IDOC`.

**Test harness**: an endpoint with `Inbound.Harness` set (`Tenant.Inbound["/http/cpictl/test"] =
&Inbound{Artifact: "CPICTL_Test_Harness", Harness: true}`, live mode) behaves like the cpictl test
harness flow: it runs the deployed flow whose ProcessDirect sender listens on the address in the
header `CpictlTargetAddress`, logs its own message with the same correlation ID (the flow's message
has it as predecessor) and answers with the body passed through, or 500 with the error. The demo
landscape does not deploy a harness; the testrun tests add one.

Send test messages with `cpictl send --idoc` and the OData flags ([testing.md](testing.md#idoc-and-odata-senders)):

```bash
cpictl idoc template --type ORDERS05 --mestyp ORDERS --sndprn S4HCLNT100 --rcvprn CPI --out orders.xml
cpictl send --artifact-id Orders_IDoc_In --idoc orders.xml --wait 60s
cpictl send --artifact-id Orders_OData_Service --odata-method POST --entity-set SalesOrders --body '{"OrderNo":"4711"}'
```

## Execution

The mock runs flows the way the message processing logs show them. No script or mapping is
executed: the payload passes through unchanged.

- **One run per flow** with the steps of the integration process (from the start event along the
  first outgoing flow), each with a duration.
- **ProcessDirect** calls the flow that listens on the address (after parameter substitution)
  synchronously: same correlation ID, `PredecessorMessageGuid` set, and a failure there fails the
  caller with the same error. No deployed consumer: `no consumer for address …`.
- **JMS** hands the message to the flow that consumes the queue about a second later: same
  correlation ID, no predecessor (cpictl links them by correlation ID). A failing JMS consumer
  ends in `RETRY` and its message stays in the queue as a failed message (`jms messages`; demo:
  `Orders_Billing`), where `jms retry`, `move` and `delete` act on it (a retry counts the attempt,
  the flow does not run again). No consumer: the message stays in the queue (nothing is logged).
  Queues exist once a flow that reads them is deployed; `jms activate` / `deactivate` set their
  state.
- **Other receivers** (HTTP, OData, SOAP, SFTP, …) are answered by the landscape's **systems**: the
  receiver's host (from the URL or the `host` property, parameters applied) is matched against
  each system's `match` pattern. The system's `latencyMs` adds to the run; with `failRate` the call
  fails with `error` (`{host}`, `{key}`, `{status}` replaced). A host no system matches answers in
  100 ms without failing.
- A receiver whose `credentialName` (SFTP: `credential_name`) does not exist on the tenant fails with
  `credential <name> not found on this tenant` (so a missing credential shows in the logs, not only
  in `transport check`).
- **Integration connections** are derived from the running flows: per flow and external receiver
  (not ProcessDirect or JMS) the first sender adapter to the receiver's host. How a tenant names
  sender hosts is not known yet, so treat the sender side as an approximation.
- **Check** (`validate`) runs a structural check of the flow and answers like a tenant:
  `Check execution result: Passed`, or `Failed` followed by the findings as SAP's JSON array
  (`severity`, `message`, `sourceObject`, `resourcePath`, `resourceName`). It reports required
  channel attributes left empty (ProcessDirect / HTTPS / HTTP / JMS / SFTP / Mail), JMS sender
  values that are not whole numbers, invalid mail addresses and Groovy steps whose script file is
  missing. It is not SAP's full Check: a flow the mock passes can still fail on a tenant. The demo
  flows pass both (verified on a real tenant).
- The Check also checks **component versions against the runtime profile** (`integrationcell`),
  using a component catalogue (see [Component catalogue](#component-catalogue)), with the
  tenant's messages:
  - a channel whose variant URI (`cmdVariantUri`) names no variant the catalogue knows (e.g. the
    old shape `ctype::AdapterVariant/cname::sap:JMS/tp::JMS/direction::Receiver`): `Enter adapter
    details for channel`;
  - a channel whose version the profile does not support: `This component HTTP with version 1.0
    is not supported in integrationcell profile.` The version is the channel's `componentVersion`
    (without it the tenant reads 1.0). Not supported: a version newer than the catalogue offers
    (`componentVersion` above its major.minor, or the URI's version above it), and 1.0 of an
    adapter that has a newer version (what a real tenant answered for HTTPS, HTTP, ProcessDirect
    and JMS channels with 1.0);
  - a step whose variant URI version is newer than the catalogue offers (e.g. `GroovyScript`
    `2.1.0` where the editor offers `2.0.0`).

  The `sourceObject` of these findings is `ComponentMetadataEditor/eid:<id>/etype:<type>/location:<name>`
  (no `pid`). In Go tests `Tenant.NoComponentCheck` turns the version check off.
- A failed step has the error and one **trace** (payload, headers, `CamelExceptionCaught`), so
  `logs steps` and `logs trace` show something.
- **Attachments**: a step whose script writes an attachment (`addAttachmentAsString("Invoice", …)`,
  `addAttachmentAsBinary`) adds one with that name and the payload to the run's log (demo:
  `Billing_Post` attaches `Invoice`, so failed postings have a trace and an attachment for
  `logs payload`).
- **Business key**: a run gets the landscape's key headers as custom header properties when the
  flow's scripts write them (`addCustomHeaderProperty("OrderNo", …)`), and the key as
  `ApplicationMessageId` when they set `SAP_ApplicationID`. A received message's key is taken from
  the `SAP_ApplicationID` header, a key header sent as HTTP header, or `<OrderNo>…</OrderNo>` in
  the payload. `MessageProcessingLogCustomHeaderProperties` answers `$filter` on `Name` and
  `Value` (`eq`) with `$expand=Log` like the tenant (`logs search`), and step properties come
  with `RunSteps?$expand=RunStepProperties` when a step has any.
- **Traffic**: at start, the `traffic` rules generate the message history (`history`, default
  24 h); runs that would end in the future are left out. The random source is derived from the
  landscape and the tier (or `seed`), so a tier always generates the same history and tiers
  differ. `--live-traffic <speed>` keeps generating messages in real time (`60`: an hour per
  minute): at most one message per millisecond and rule, however high the speed.

## Component catalogue

The version check uses a component catalogue in the format of `cpictl components`
(`.cpi/components.json`). Built in: SAP's editor metadata of an `integrationcell` tenant (Web UI,
October 2026; `internal/cpitest/components.json`). A landscape can bring its own, for the whole
landscape or per tier (a tenant on another release), with a path relative to the landscape
directory:

```yaml
components: components.json            # cpictl components import <editor metadata> writes this format
tiers:
  - name: prod
    components: components-prod.json   # this tier's tenant
```

`cpictl components import` turns the editor metadata the Web UI loads (`/api/1.0/metadata`) into
such a file. In Go tests: `Tenant.Components` (nil: the built-in catalogue).

## Admin API (`/_mock/...`)

Tests and demos change the running mock over HTTP instead of restarting it. The admin API is not
part of the SAP API and is protected by a token, TLS or not (encryption is not authorization):

- Every request needs `Authorization: Bearer <token>`. The token is `--admin-token <value>`; without
  it the mock generates a random one at start and prints it as `CPICTL_MOCK_ADMIN_TOKEN=...`.
- `pkg/mocktenant` has no token by default: then only loopback clients are allowed. Set
  `m.AdminToken` to require one from every client.
- A request without the token, or with a wrong one, is answered with 403.

| Method and path | Body | Effect |
|-----------------|------|--------|
| `GET /_mock/systems` | | the tier's systems |
| `PUT /_mock/systems/<name>` | `{"match", "latencyMs", "failRate", "status", "error"}` | add or change a system (e.g. `failRate: 1`: it is down) |
| `POST /_mock/run` | `{"artifact", "key", "payload", "count"}` | run a deployed flow now, `count` up to 1000 times (also timer and ProcessDirect flows); returns `{runs: [{messageGuid, status, error}]}` |
| `POST /_mock/messagelogs` | `[{"Guid", "Artifact", "Status", "CorrelationID", "ErrorText", "Headers", "Steps", ...}]` | add message logs as they are; answers `{"added": n, "kept": k}` (`k < n` when the retention or the cap dropped some) |
| `POST /_mock/faults` | `{"pathPrefix": "/api/v1/IntegrationPackages", "status": 401, "count": 2}` | the next `count` requests on the path answer `status` (expired login, 429, 503 …); `"count": -1` keeps answering until `DELETE`; `"message"` is sent as the tenant's OData error body, e.g. `{"pathPrefix": "/api/v1/LogFiles", "status": 501, "count": -1, "message": "Not implemented"}` to make an API area answer like a tenant that does not offer it |
| `DELETE /_mock/faults` | | drop pending faults |
| `GET /_mock/state` / `PUT /_mock/state` | the exported state | export the whole tenant (content, security material, Partner Directory, logs, systems) and load it into another mock |

**`/_mock/state` contains secrets.** The export has the credentials' stored secret fields (passwords, client secrets, as put into the mock) and the content of all artifacts (scripts, models, parameters), and the logs. That is fine for mock data. Do not load real customer secrets into a mock: a real tenant never returns them, and anyone holding the admin token can read them back from this endpoint.

```bash
TOKEN=<CPICTL_MOCK_ADMIN_TOKEN from the start output>
curl -H "Authorization: Bearer $TOKEN" -X PUT localhost:8081/_mock/systems/finance -d '{"match":"finance-*.example.com","failRate":1,"error":"finance down for {key}"}'
curl -H "Authorization: Bearer $TOKEN" -X POST localhost:8081/_mock/run -d '{"artifact":"Billing_Post","key":"4711"}'
```

## From other containers

cpictl accepts plain `http://` only for loopback hosts, so credentials never travel unencrypted.
To reach the mock from another container, serve HTTPS with a generated certificate and give the
client the CA:

```bash
cpictl mock-tenant --tier prod --addr 0.0.0.0:8443 --tls \
  --tls-hosts mock-prod,localhost --ca-out /certs/mock-ca.pem --public-url https://mock-prod:8443
# client container
SSL_CERT_FILE=/certs/mock-ca.pem CPICTL_TMN_HOST=https://mock-prod:8443 CPICTL_TMN_USERID=mock CPICTL_TMN_PASSWORD=mock cpictl status
```

`--public-url` is the base of the flows' endpoint URLs in `ServiceEndpoints` (what `send` calls);
by default the listen address.

Docker Compose example:

```yaml
services:
  mock-dev:
    image: <your image with cpictl>
    command: ["cpictl", "mock-tenant", "--tier", "dev", "--addr", "0.0.0.0:8443", "--tls",
              "--tls-hosts", "mock-dev", "--ca-out", "/certs/mock-dev.pem", "--public-url", "https://mock-dev:8443"]
    volumes: ["certs:/certs"]
volumes:
  certs: {}
```

## In Go tests

`github.com/cpars-innovation/cpicli/pkg/mocktenant` is the same mock as a library, for tests of
tools built on cpicli.

> **Experimental:** the API may change in minor versions until cpicli 1.0.

Supported entry points: `Serve` and `Start` (a live mock on your listener or on a free loopback
port), `SeedDemo`, `SeedDir` and `SeedLandscape` (content; `LoadLandscapeDir` reads a landscape),
`Tenant.Auth` ([credentials](#credentials)), `Tenant.MessageLogs` (what the mock logged), and the [admin API](#admin-api-_mock) (set
`Tenant.AdminToken` to require a bearer token from every client, otherwise only loopback clients
are allowed). `Tenant` and the other types are aliases of internal types: besides the entry points,
rely only on fields such as `Artifacts`, `URL()` and `Executer()`; the test-scripting fields
(`AfterDeploy`, `StatusOverride`, ...) may change.

```go
m := mocktenant.Start() // live, Basic Auth with CSRF and OAuth, on a free loopback port
defer m.Close()
if err := mocktenant.SeedDir(m, "testdata/landscapes/retail-b", "prod-eu", time.Now()); err != nil {
	t.Fatal(err)
}
// point the code under test at m.URL(); read what happened with m.MessageLogs(), m.Artifacts …
```
